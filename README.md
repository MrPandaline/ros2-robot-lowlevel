# ros2-robot — STM32F411 low-level firmware

STM32CubeIDE firmware for an STM32F411CEU6 controlling a
differential-drive robot with a 5-servo manipulator arm, an MPU6050 IMU, an INA226 power
monitor, and wheel encoders. The MCU talks to a **micro-ROS agent running on a separate
Orange Pi** (not part of this repo) over UART, bridging it into a full ROS 2 project. The
Orange Pi also drives an LD06 lidar — not part of this
repository, but this is the system the firmware is designed to plug into.

## Hardware

- MCU: STM32F411CEU6, clocked from a 25MHz HSE quartz crystal.
- Motors: differential drive via a TB6612FNG.
- Servos: 5-channel servo motor manipulator arm.
- Sensors: MPU6050, INA226, quadrature wheel encoders made with SS41F Hall sensors.
- Link to the rest of the ROS 2 stack through UART micro-ROS agent on an Orange Pi.

## Repository layout

```
Core/                           Application source code (main.c, app_main.cpp, peripherals, ...)
Drivers/, Middlewares/          STM32 HAL/CMSIS/FreeRTOS — vendor code, not committed
                                 (regenerated by CubeMX from ros2-robot.ioc)
micro_ros_stm32cubemx_utils/    micro-ROS static library + transport code
ros2-robot.ioc                  CubeMX peripheral and clock configuration
```

## Prerequisites

- [STM32CubeIDE](https://www.st.com/en/development-tools/stm32cubeide.html) (this is a
  plain CubeIDE Managed Build project — `.project`, `.cproject`, `.mxproject` — not a
  standalone CMake/Makefile project you build with a bare `arm-none-eabi-gcc` on `PATH`).
- An ST-Link (onboard or external) to flash and debug MCU.
- Docker, only if you need to rebuild the micro-ROS static library.
- A machine running `micro_ros_agent` reachable over UART from the board (see
  [Running the robot](#running-the-robot-orange-pi-side) below) — an Orange Pi in the
  reference setup, but any Linux host with a free UART or USB-UART will do.

## Building & flashing with STM32CubeIDE

1. Clone this repo and open it in STM32CubeIDE (`File / Open Projects from File System`,
   point it at the repo root).
2. `Drivers/`/`Middlewares/` are gitignored (vendor CubeMX/HAL/FreeRTOS code) and importing
   the project does **not** regenerate them by itself — open `ros2-robot.ioc` and click
   *Generate Code* (Device Configuration Tool) once, or the first build will fail with
   missing HAL headers.
3. Make sure the micro-ROS static library is present at
   `micro_ros_stm32cubemx_utils/microros_static_library_ide/libmicroros/` (see below if
   it's missing or out of date).
4. Build (`Project / Build`). This drives `Debug/makefile`, which CubeIDE regenerates —
   the **symlinked** `Makefile` at the repo root points there, and is only meant to be
   invoked via CubeIDE's bundled ARM toolchain.
5. Flash with an ST-Link via CubeIDE's Run configuration for this project.

If you ever touch clock config in the `.ioc`, keep the PLL source on HSE (`PLLM=25,
PLLN=192, PLLP=DIV2` ) — timer-derived signals (UART baud, servo PWM pulse widths) need a better clock device than a regular HSI.

## Rebuilding the micro-ROS static library

`micro_ros_stm32cubemx_utils/microros_static_library_ide/libmicroros/` is a prebuilt 
library, not source — it must match the ROS distro of whatever `micro_ros_agent` it talks
to (a distro mismatch here silently corrupts CDR framing on the first real publish). Rebuild
it like this:

**1. Clone the micro-ROS utils into the project folder (on the host):**

```bash
cd ~/stm32_projects/ros2-robot
git clone https://github.com/micro-ROS/micro_ros_stm32cubemx_utils.git
```

**2. Make sure you have a real Makefile.** Since the project is built through CubeIDE's
Managed Build, the Makefile only exists under `Debug/`:

```bash
find ~/stm32_projects/ros2-robot -iname "makefile" -o -iname "Makefile"
```

The micro-ROS Docker build script looks for a Makefile **at the project root**. This repo
already ships that as a tracked symlink (`Makefile -> Debug/makefile`), so a fresh clone
has it out of the box. If yours is somehow missing, either:
- *copy* the flags you need out of `Debug/makefile` into a separate config, or
- *symlink* it: `ln -s Debug/makefile Makefile` (may not work perfectly, but worth trying
  first).

**3. Build the static library (on the host, not inside a container you're already in):**

```bash
cd ~/stm32_projects/ros2-robot
docker pull microros/micro_ros_static_library_builder:humble

docker run --rm -v $(pwd):/project \
  --env MICROROS_LIBRARY_FOLDER=micro_ros_stm32cubemx_utils/microros_static_library_ide \
  microros/micro_ros_static_library_builder:humble
```

Use whatever ROS distro tag matches your `micro_ros_agent` (e.g. `humble`) — `--network
host` helps if the default bridge network has trouble resolving GitHub during the
dependency clone. The script prints the CFLAGS it auto-detected (target architecture, `-D`
defines like `-DSTM32F411xE`) — confirm those match your MCU (Enter/Y).

If autodetection doesn't work, you'll need to supply the flags explicitly: open the
CubeIDE-generated `Debug/makefile`, find the lines with `-D` defines and `-I` include
paths, and copy them into `micro_ros_stm32cubemx_utils/microros_static_library_ide/micro_ros_stm32cubemx_utils/config.mk`.

**4. Wire the library into the CubeIDE project** :

Right-click the project / *Properties* / *C/C++ Build* / *Settings*.

*MCU GCC Linker* / *Libraries:*
- **Library search path (-L)**: add
  `../micro_ros_stm32cubemx_utils/microros_static_library_ide/libmicroros`
- **Libraries (-l)**: add `microros`

*MCU GCC Compiler → Include paths:*
- add `../micro_ros_stm32cubemx_utils/microros_static_library_ide/libmicroros/microros_include`

*Add the extra transport/support sources to the project:*

Copy the files you need from `micro_ros_stm32cubemx_utils/extra_sources/` into
`Core/Src/` (or add the folder as a source location via *Properties* / *C/C++ General* /
*Paths and Symbols* / *Source Location* / *Add Folder*):
- `custom_memory_manager.c`
- `microros_allocators.c`
- `microros_time.c`
- `microros_transports/dma_transport.c` (if you're using DMA — this repo does, see
  `micro_ros_stm32cubemx_utils/extra_sources/microros_transports/dma_transport.c`) — a
  plain interrupt-based UART transport needs its own transport code instead on F411.

After that, rebuild the project as described above.

### `dma_transport.c`

This file originates from the `micro_ros_stm32cubemx_utils` vendor repo
(`extra_sources/microros_transports/dma_transport.c`), with local modifications for this
board's UART+DMA setup — it's the XRCE-DDS transport wired up via
`rmw_uros_set_custom_transport()` in `app_main.cpp`, since micro-ROS doesn't ship one ready
for an arbitrary CubeMX configuration out of the box. This repo tracks only this one
modified file out of the whole vendor clone (see `.gitignore`); the rest of that repository
is unmodified vendor code you re-clone per the steps above, not something maintained here.

- **RX**: `HAL_UART_Receive_DMA()` runs in circular mode into a 2048-byte ring buffer
  (`dma_buffer`). `cubemx_transport_read()` reads how far the DMA controller has written via
  `__HAL_DMA_GET_COUNTER()` and drains whatever's new — no per-byte interrupt overhead.
- **TX**: `HAL_UART_Transmit_DMA()`, with a short poll loop waiting for
  `uart->gState == HAL_UART_STATE_READY` (100ms timeout) before returning.
- **Recovery**: both `cubemx_transport_open()` and `cubemx_transport_write()` defensively
  clear the UART error flags (`OREF`/`NEF`/`FEF`/`PEF`) and reset `uart->gState` if the
  peripheral is found in a stuck non-ready state. This matters together with
  `HAL_UART_ErrorCallback()` in `main.c`, which uses `HAL_UART_AbortReceive()` rather than
  `HAL_UART_DMAStop()` on a line error — so an RX glitch doesn't tear down an in-flight TX
  DMA transfer and corrupt an outgoing XRCE frame mid-send.

## Running the robot (Orange Pi side)

None of this runs on the STM32 — it's the companion setup needed to actually talk to the
board and use the lidar.

### micro-ROS agent (bridges the STM32 into ROS 2)

```bash
ros2 run micro_ros_agent micro_ros_agent serial --dev /dev/ttyS7 -b 115200
```

`/dev/ttyS7` is the Orange Pi UART wired to the STM32; the baud rate must match
`huart1.Init.BaudRate` in `main.c` (mirrored in `ros2-robot.ioc` as `USART1.BaudRate`). The
board auto-reconnects on its own if the agent restarts — no need to reset the STM32, just
re-run this command. 

Making this project I noticed that Orange Pi 4 Pro has an issue with 
UART connectivity with baudrates higher than 115200 through GPIO UART. 
You can inspect this with this commands:
```bash
sudo dmesg -C
sudo stty -F /dev/ttyS7 230400 
sudo dmesg
```

You'll get something like:
```text
[   51.959703] sunxi:uart-ng-uart-ng7:[INFO]: uart7, select set 1, 
baud 230400, uartclk 24000000 beyond rance[30000000, 120000000]
```

This message appears because Orange Pi hardware UART timer frequency is 24MHz, which is 
below minimum for standard baudrates higher than 115200. You can change clocking timer for UART only if you recompile the OS kernel from source. 

### Lidar (LD06, on the Orange Pi)

Motor speed is a raw PWM sysfs channel (`PWM0_7` = `pwmchip0`/`pwm7`) and does **not**
persist across Orange Pi reboots — redo this after every reboot before launching the
driver (or make a systemd service):

```bash
echo 7 | sudo tee /sys/class/pwm/pwmchip0/export        # errors "busy" if already exported — fine, continue
echo 33333 | sudo tee /sys/class/pwm/pwmchip0/pwm7/period       # 30kHz
echo 13333 | sudo tee /sys/class/pwm/pwmchip0/pwm7/duty_cycle   # 40% duty ~ 10Hz scan rate
echo normal | sudo tee /sys/class/pwm/pwmchip0/pwm7/polarity    # default is "inversed" — must be set explicitly
echo 1 | sudo tee /sys/class/pwm/pwmchip0/pwm7/enable
```

Scan data comes over a **separate USB-UART adapter** (`/dev/ttyUSB0`, 230400 baud), not the
onboard UART. Driver lives in
`~/ros2_ws/src/ldlidar_stl_ros2` on the Orange Pi (not this repo):

```bash
source ~/ros2_ws/install/setup.bash
ros2 launch ldlidar_stl_ros2 ld06.launch.py   # already configured for /dev/ttyUSB0 @ 230400
```

Verify with `ros2 topic hz /scan` (should read ~10Hz at the duty cycle above).

### Teleop

Drive (publishes `geometry_msgs/Twist` to `cmd_vel`, matching the STM32 subscriber):

```bash
ros2 run teleop_twist_keyboard teleop_twist_keyboard
```

| Topic | Type | Rate | Direction |
|---|---|---|---|

| `battery_state` | `sensor_msgs/BatteryState` | 1000ms | pub |
| `cmd_vel` | `geometry_msgs/Twist` | — | sub |
| `servo_cmd` | `std_msgs/Float32MultiArray` | — | sub (must be exactly 5 elements) |
